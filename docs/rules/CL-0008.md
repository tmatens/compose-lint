# CL-0008: network_mode: host — risks and alternatives

**Severity:** HIGH ([how it is derived](#severity-derivation))

`network_mode: host` puts the container on the host's own network stack: every
interface, every port, and the services the host keeps on `127.0.0.1`. Remove
it and publish the ports the service needs.

## Fix

Remove `network_mode: host` and use bridge networking with explicit port mappings:

```yaml
services:
  web:
    image: nginx:1.27-alpine
    ports:
      - "127.0.0.1:8080:80"     # host port 8080 on loopback, nginx's port 80
    networks:
      - app-network

networks:
  app-network:
```

1. **Publish what clients reach, bound to an address.** Each port the service
   listens on for outside clients needs a `ports:` entry; bind it to
   `127.0.0.1` or the host's LAN address ([CL-0005](CL-0005.md#fix)).
   Under host networking those ports were on every interface, and UFW and
   firewalld did not stand in front of them.

2. **If the service talked to something on the host, give it a route to the
   host instead of the host's network.** Add the host's gateway name, and make
   sure the host service listens on an address the bridge can reach:

   ```yaml
   services:
     app:
       image: myapp:1.0
       extra_hosts:
         - "host.docker.internal:host-gateway"   # the host, seen from the bridge
   ```

   The app then connects to `host.docker.internal`. A host service bound to the
   Docker bridge's address (`ip -4 addr show docker0`) answered from a bridge
   container; the same service bound only to `127.0.0.1` did not, which is the
   isolation this change is buying.

3. **Check the container has its own network:**

   ```bash
   docker compose up -d web
   docker compose exec web ip -o -4 addr | awk '{print $2}'
   # lo
   # eth0
   ```

   Under `network_mode: host` the same command listed every host interface
   (`wlan0`, `docker0` and each bridge on the test host).

4. **Check the finding is gone:**

   ```bash
   compose-lint -q compose.yaml | grep CL-0008    # prints nothing once fixed
   ```

Verified against Docker 29.7.2 with `nginx:1.27-alpine` and `busybox:1.37`.

Only workloads that genuinely need to see host traffic (network monitoring,
certain VPN agents, eBPF-based tools) require host networking.

`network_mode: host` is also the most-extreme version of CL-0005's iptables-bypass concern: port-publish rules don't apply, so anything the container binds is on the host's interfaces directly. UFW / firewalld will not protect those bindings.

**Tested on:** Docker 29.7.2 with Compose 5.5.0, on a host without AppArmor (Yama `ptrace_scope` 1); the Fix steps above were re-run there in October 2026. **Not tested:** an AppArmor or SELinux host.

## When to suppress

- Network-monitoring sidecars (cAdvisor, node-exporter, Netdata) that legitimately need host-namespace visibility.
- Userspace VPN agents that manage host routing tables.

In both cases suppress with a `reason:` naming the workload, and pair with `cap_drop`, `read_only`, and `no-new-privileges` to harden whatever isolation remains.

## What it detects

Any service with `network_mode: host`. Other network modes (`bridge`, `service:`, custom networks) are not flagged.

A service with no `networks:` key is not flagged either. Compose attaches it to
the project's own `<project>_default` network, a user-defined bridge created for
that project, so the host's default `docker0` bridge that CIS Docker Benchmark
5.30 asks not to use is avoided by construction. Whether two services of one
project should be able to reach each other is a design decision the file does
not settle, and no rule grades intra-project reachability.

## Why it matters

Host network mode disables Docker's network isolation entirely. The container:

- Shares the host's IP address and all network interfaces
- Can bind to any port on the host without publishing
- Can observe and capture all host network traffic
- Can communicate with services bound to `127.0.0.1` on the host
- Bypasses Docker network policies and inter-container firewalling

This is a significant isolation bypass — any network-based security boundary between the container and the host is removed.

## Severity derivation

**Derivation** (see [severity model](../severity.md)):

- **Baseline:** A — the attacker already has code execution in this container, as the workload uid
- **Precondition:** Technique — the host network namespace is handed over immediately, but turning that into impact takes a published technique: packet capture, ARP spoofing, or abusing a service that trusts `127.0.0.1`
- **Impact:** Cross-container — the reach is every interface and every other container's routed traffic, plus host-loopback services. It is a pivot, not host control
- **Qualifier/modifier:** none
- **Derived:** Technique × Cross-container = HIGH
- **Shipped:** HIGH
- **Evidence:** `_cl0008` — a host-network container sees the host's interfaces, verified live
