# CL-0015: Healthcheck explicitly disabled

**Severity:** LOW

**Derivation** (see [severity model](../severity.md)):

- **Baseline:** A — the attacker already has code execution in this container, as the workload uid
- **Precondition:** Removes a mitigation — clearing the healthcheck grants nothing. It removes one automated signal that the right process is still the one running
- **Impact:** Single container
- **Qualifier/modifier:** none
- **Derived:** Removes a mitigation × Single container = LOW
- **Shipped:** LOW
- **Evidence:** No premise check. The behaviour is a Compose spec property — `disable: true` and `test: ["NONE"]` clear an image's inherited `HEALTHCHECK` — and the security claim is about what an operator can no longer observe, which is not a runtime state a container test can assert

**References:**
- CIS Docker Benchmark 4.6 — Ensure that HEALTHCHECK instructions have been added to container images
- CIS Docker Benchmark 5.27 — Ensure that container health is checked at runtime

## What it detects

Services that explicitly disable their healthcheck, in either form: `healthcheck.disable: true`, or a `healthcheck.test` of `["NONE"]` / `"NONE"` (the Compose spec's way of clearing an image's inherited healthcheck). Services without a healthcheck configuration, or with `disable: false`, are not flagged — this rule targets explicit opt-outs only.

## Why it matters

The security angle is narrow but real: a container that is *running but compromised* — for example, an attacker has crashed the legitimate process and replaced it with a reverse shell that doesn't pass the healthcheck — looks healthy to the orchestrator without `HEALTHCHECK`. Healthchecks are a weak signal of "the workload is doing the thing it's supposed to," and disabling them removes one of the few automated tripwires that distinguishes "process is alive" from "the right process is alive." Disabling also overrides any `HEALTHCHECK` instruction in the Dockerfile, which the image author may have written specifically because of a known stuck-but-listening failure mode.

This is the lowest-severity rule for a reason. It is more reliability than security, and a well-architected system should not depend on `HEALTHCHECK` for incident detection. It is included because the explicit-disable case is rare and worth a question.

## Fix

Remove `disable: true` and configure an appropriate healthcheck:

```yaml
# Before
services:
  app:
    image: myapp:1.0
    healthcheck:
      disable: true

# After
services:
  app:
    image: myapp:1.0
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost/"]
      interval: 30s
      timeout: 10s
      retries: 3
```

If the image already has a `HEALTHCHECK` instruction, simply removing the `healthcheck:` block entirely will restore the image's built-in check.
