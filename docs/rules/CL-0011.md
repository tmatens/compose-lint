# CL-0011: cap_add: NET_ADMIN, BPF, SYS_BOOT

**Severity:** HIGH ([how it is derived](#severity-derivation))

The service adds `NET_ADMIN`, `BPF` or `SYS_BOOT`, each of which reaches other
containers or the host. Remove it unless managing interfaces, loading BPF
programs or rebooting the host is the service's job, and then keep it as the
only capability the service holds.

## Fix

A common case is a VPN container set up from a kernel-mode example.
Tailscale's image runs in userspace networking mode by default, which needs no
capability at all:

```yaml
# Before
services:
  tailscale:
    image: tailscale/tailscale:v1.104.1
    cap_add:
      - NET_ADMIN
    devices:
      - /dev/net/tun:/dev/net/tun
    environment:
      TS_USERSPACE: "false"

# After: userspace networking, the image's default
services:
  tailscale:
    image: tailscale/tailscale:v1.104.1
    cap_drop:
      - ALL
```

1. **Remove the capability and see whether the service still does its job.**
   This is the drop-and-observe loop on [CL-0006](CL-0006.md#fix). Read the
   logs, not only the container state: Tailscale in kernel mode without
   `NET_ADMIN` stays `running` while its daemon has failed with

   ```
   wgengine.NewUserspaceEngine(tun "tailscale0") error: tstun.New("tailscale0"): operation not permitted
   ```

   (captured on Docker 29.7.2, not CI-asserted).

   A missing `NET_ADMIN` elsewhere usually reads
   `ip: RTNETLINK answers: Operation not permitted`.

2. **Prefer a mode that does not need it.** In Tailscale's userspace mode there
   is no `tailscale0` interface; other processes reach the tailnet through the
   daemon's SOCKS5 or HTTP proxy
   ([Tailscale: userspace networking](https://tailscale.com/kb/1112/userspace-networking)).
   Under `cap_drop: [ALL]` it logs two warnings about UDP buffer sizes, marked
   `impacts throughput only`, and a `tstun` line about tun device stats; all
   three appear at default capabilities too, so none is caused by the drop.

3. **If the capability is genuinely needed, make it the only one, and record
   why.** A kernel-mode VPN or a router container needs `NET_ADMIN` to manage
   its interface and routes:

   ```yaml
   services:
     vpn:
       image: tailscale/tailscale:v1.104.1
       cap_drop:
         - ALL
       cap_add:
         - NET_ADMIN
       devices:
         - /dev/net/tun:/dev/net/tun
       environment:
         TS_USERSPACE: "false"
   ```

   ```yaml
   # .compose-lint.yml
   rules:
     CL-0011:
       exclude_services:
         vpn: "kernel-mode WireGuard interface needs NET_ADMIN; reviewed 2026-10"
   ```

   `NET_ADMIN` reaches the containers on the networks this service joins, so
   keep it off networks it has no reason to share.

4. **Check what the container holds.** `CapBnd` in `/proc/1/status` is the most
   any process in the container can hold
   ([CL-0006](CL-0006.md#fix) explains reading it):

   ```bash
   docker compose exec vpn grep CapBnd /proc/1/status
   # CapBnd:	0000000000001000
   capsh --decode=0000000000001000        # on the host, from libcap
   # 0x0000000000001000=cap_net_admin
   ```

5. **Check the finding:**

   ```bash
   compose-lint -q compose.yaml | grep CL-0011
   ```

   It prints nothing once the capability is gone. A suppressed service still
   prints its line, marked `SUPPRESSED`, with your reason in the full output.

Verified against Docker 29.7.2 and `tailscale/tailscale:v1.104.1`: userspace
mode starts under `cap_drop: [ALL]`; kernel mode fails without `NET_ADMIN` and
starts with it as the only capability.

`BPF` and `SYS_BOOT` have no common no-capability alternative: a tool that loads
BPF programs or reboots the host needs them, which is reason to ask whether
that tool belongs in a container. Keep them as the only capability and suppress
the same way.

**Tested on:** Docker 29.7.2 with Compose 5.5.0, on a host without AppArmor (Yama `ptrace_scope` 1); the Fix steps above were re-run there in October 2026. Also measured in throwaway VMs in October 2026 (Docker 29.9.1 or 29.1.3): on Ubuntu 24.04 with AppArmor, `kexec_load` with `SYS_BOOT` returned `Operation not permitted` under the default seccomp profile and succeeded only with seccomp unconfined. **Not tested:** SELinux.

## What it detects

`cap_add` entries naming a capability that reaches past this container without
handing over host code execution outright:

| Capability | Grants |
|---|---|
| `NET_ADMIN` | reconfigure interfaces, routes and firewall rules — transparent interception of other containers' traffic, which `NET_RAW` alone cannot reach |
| `BPF` | load BPF programs — kernel introspection and manipulation, and a recurring container-escape surface |
| `SYS_BOOT` | reboot or power off the host via `reboot(2)`. It does **not** load a kernel via kexec: `kexec_load(2)` returns EPERM even with the capability held (verified on Docker 29.1.3) — the default seccomp profile blocks it outright rather than gating it on a capability |

`CAP_`-prefixed and lowercase spellings are matched the same way: Docker treats
`CAP_NET_ADMIN` and `NET_ADMIN` as the same capability.

**This rule is one of six over `cap_add`**, split by what the capability
grants, because SARIF advertises `security-severity` on the rule descriptor and
a rule carrying two severities misreports one of them:

| Rule | Tier | Members |
|---|---|---|
| [CL-0024](CL-0024.md) | CRITICAL | `ALL`, `SYS_ADMIN`, `SYS_MODULE`, `SYS_RAWIO` |
| **CL-0011** | **HIGH** | `NET_ADMIN`, `BPF`, `SYS_BOOT` |
| [CL-0028](CL-0028.md) | HIGH | `SYS_TIME`, `PERFMON` |
| [CL-0029](CL-0029.md) | HIGH | `SYS_NICE`, `IPC_LOCK`, `LEASE` |
| [CL-0030](CL-0030.md) | HIGH | `SYSLOG` |
| [CL-0027](CL-0027.md) | MEDIUM | `SYS_PTRACE`, `DAC_READ_SEARCH` |

Safe capabilities such as `NET_BIND_SERVICE` and `CHOWN` are not flagged by any
of the six. Neither are `MKNOD`, `SYS_CHROOT` and `DAC_OVERRIDE`: all three
are in Docker's default set, so flagging them on `cap_add` scored the
*declaration* rather than the runtime state, and inverted the gate —
`cap_drop: [ALL]` plus `cap_add: [DAC_OVERRIDE]` (one capability) failed at the
default `--fail-on high`, while no `cap_drop` at all (fourteen capabilities,
`DAC_OVERRIDE` among them) passed (issue #492).

## Why it matters

Linux capabilities split root's privileges into discrete units, and these three
are the ones that reach other containers or the host without being an escape on
their own.

`NET_ADMIN` is the one to understand first, because it is the capability people
add casually for VPN and networking containers. It is strictly more than
`NET_RAW` ([CL-0006](CL-0006.md)): `NET_RAW` buys interception and denial of
service against an L2 neighbour, while `NET_ADMIN` adds the routing and
`ip_forward` control needed for a *transparent* man-in-the-middle that the
victim cannot detect from its own connectivity.

`BPF` is a kernel read/write primitive on modern kernels and a recurring escape
surface. `SYS_BOOT` is availability only — but host availability, which no other
rule in the set reaches.

## Severity derivation

**Derivation** (see [severity model](../severity.md)):

- **Baseline:** A — the attacker already has code execution in this container, as the workload uid
- **Precondition:** Technique — each member is a primitive that needs a published technique to become impact: ARP or route manipulation for `NET_ADMIN`, a BPF-based kernel attack, a reboot as a denial of service
- **Impact:** Cross-container — traffic interception across containers on the host, kernel manipulation shared by all of them, or host availability
- **Qualifier/modifier:** none
- **Derived:** Technique × Cross-container = HIGH
- **Shipped:** HIGH
- **Evidence:** `_cl0011` proves only that `cap_add` deposits the capability into the effective set — it does not exercise any member's reach. The cross-container impact (`NET_ADMIN` traffic manipulation on a shared Docker network, `BPF` kernel access) is reasoned from the capabilities' semantics under Docker's default seccomp profile; `_t_net_admin` covers only an in-netns route change, not cross-container interception. One member claim *is* empirically pinned: `SYS_BOOT`'s kexec story is refuted, not assumed — `kexec_load` returns EPERM even with the capability held (captured on Docker 29.1.3), so the documented grant is `reboot(2)`
